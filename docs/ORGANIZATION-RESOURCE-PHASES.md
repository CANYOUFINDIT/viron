# 组织与资源授权实施阶段

状态：实施顺序。产品规则以 [组织、角色与资源授权设计约定](./ORGANIZATION-RESOURCE-DESIGN.md) 为准。本文件不另立规则；原型与设计约定不一致时，按设计约定实施。

日期：2026-10-11。

依据：

- 设计约定：[ORGANIZATION-RESOURCE-DESIGN.md](./ORGANIZATION-RESOURCE-DESIGN.md)
- 参考原型：[prototypes/organization-resources.html](../prototypes/organization-resources.html)（存储键 `viron-org-resource-prototype-v10`）
- 当前产品基线：`dev` 上的组织工作空间。成员角色仍是 `admin` / `member`；资源使用权写在 `access_authorizations`（授权对象 + 范围 + 操作 + 有效期，环境组的「全部」包含以后新增的资源）；另有 `resource_grants`。每个组织一条 `organization_approval_workflows`。界面入口是组织架构、授权中心、邀请、平台账号。

原型中的账号、地址、人员和业务名称都是虚构示例，不能当作正式产品的默认配置。

## 1. 顺序

先换权限判定和数据，再换管理界面，然后换资源浏览，最后换申请、执行拦截和使用界面上的剩余时长。

资源总览的环境卡片可以和角色页并行画界面，但任何新的授权写入都要等阶段 0 的判定上线。按左侧菜单从上往下做，会把页面接到仍在使用的「人 + 资源 + 操作」授权上，阶段 0 之后整段返工。

四套记录在阶段 0 建表，之后分阶段开放写入和执行：

| 记录 | 回答的问题 | 保存内容 |
| --- | --- | --- |
| 角色 | 能做什么 | 权限码集合 |
| 角色分配 | 谁在什么时候持有这个角色 | 成员或子组织 + 角色 + 有效期；管理操作可另有管理范围 |
| 数据授权 | 这个角色能碰哪些资源 | 角色 + 具体资源 ID + 有效期；不含成员，不含功能开关 |
| 功能授权 | 谁能在这些资源上使用 MCP、Agent、Web 插件 | 成员或子组织 + 环境或连接 + 功能 + 有效期；不含角色 |

常规操作要同时满足：此人有效持有某个角色，该角色允许此操作，并且授予该角色的有效数据授权包含此资源。操作码和资源清单必须来自同一个角色。MCP / Agent 在此之上还要有覆盖该目标的有效功能授权。Web 插件按当前真实环境判断。语义细节见设计约定第 3 节和第 5 节。

## 2. 当前实现与目标

| 当前 `dev` | 目标 |
| --- | --- |
| `organization_members.role` 为 `admin` 或 `member`，多处接口用 `role === "admin"` 放行 | 三个普通初始角色，之后创建的角色使用同一张表；权限只来自权限码 |
| `access_authorizations` 把授权对象、资源范围和操作写在一条记录里 | 角色分配、数据授权、功能授权分开保存、分开校验 |
| 环境组选择「全部」时，以后加入该组的资源自动纳入 | 保存时固定当时的资源 ID；新增资源需另行授权 |
| 授权中心是授权的写入入口 | 角色页维护功能权限、数据权限和已授权对象；资源上的「数据授权」直接打开对应表单 |
| 每个组织一条审批流程 | 一条默认流程承接未分配连接，指定流程按连接 ID 唯一归属 |
| 邀请、平台账号与组织资源权限放在同一组页签 | 邀请留在组织架构成员操作里；平台账号仍只对平台管理员开放，不由此获得组织资源权限 |

个人工作空间所有者的既有边界保留。

## 3. 阶段总览

| 阶段 | 名称 | 前置 | 完成后用户能做什么 |
| --- | --- | --- | --- |
| 0 | 权限内核与迁移 | 无 | 新组织按新规则计算权限。旧授权已迁入，范围没有被放大。授权中心仍可查看 |
| 1 | 角色维护 | 0 | 在角色页改权限码、给角色授资源、把角色分给成员或子组织 |
| 2 | 组织架构收口 | 0、1 | 在子组织里只看成员和关联资源；邀请不再附带角色 |
| 3 | 资源总览与关联资源 | 0、1 | 用和用户端一致的六个入口浏览组织资源，并对当前资源授权或申请 |
| 4 | 我的授权、申请与待办 | 0、1 | 查看自己的角色、数据授权和功能授权；提交两类申请可待阶段 5 |
| 5 | 审批范围、两类申请与台账 | 0、1、4 | 按连接归属审批；通过后只生成对应的一种授权，并留下台账 |
| 6 | MCP、Agent、Web 插件执行 | 0、5 | 未获功能授权的环境里，自动化调用和插件执行被拒绝 |
| 7 | 剩余时长与全路径复核 | 0、3、6 | 使用界面显示限时操作的剩余时间；执行前再次校验 |

建议分四次交付：

| 交付 | 阶段 | 结果 |
| --- | --- | --- |
| 第一刀 | 0 + 1 | 用角色管理权限。旧授权中心停止写入，列表可只读 |
| 第二刀 | 2 + 3 | 从组织架构和资源总览按范围查看，并直接对当前资源授权或申请 |
| 第三刀 | 4 + 5 | 个人查看、分类申请、按连接归属审批，台账留痕 |
| 第四刀 | 6 + 7 | 自动化和插件按环境停止执行；使用界面出现剩余时长 |

## 4. 阶段说明

### 阶段 0：权限内核与迁移

建立判定函数和四张表，把现有组织成员与授权迁进去。本阶段不新增组织工作空间页面。

交付：

- 表：`roles`、`roleAssignments`、`roleDataGrants`、`resourceFeatureGrants`。字段见设计约定第 7 节。三套授权记录分别校验：分配不保存连接范围，数据授权不保存成员或功能开关，功能授权不保存 `roleId`。
- 判定函数覆盖：同一角色内的操作码与资源清单、子组织沿祖先继承、有效期与启停、多条有效授权取并集。未勾选表示未授予，不能否决另一条仍然有效的记录。
- 创建组织时生成组织管理员、普通成员、审计员，并把组织管理员分配给创建者。三个名称只描述初始内容。
- 迁移 `admin` / `member` 和现有 `access_authorizations`、`resource_grants`。整组授权在迁移时写成当时的资源 ID 清单。功能授权初始为空，不从旧的使用权限或已安装插件推断为允许。
- 组织、资源、审批、连接工具、凭据维护里用 `role === "admin"` 放行的路径，改为调用新判定。替换范围包括服务端和桌面执行路径。

本阶段不做：角色编辑界面、资源总览、审批流程拆分、插件执行拦截、剩余时长。

验收：

- 新组织只有三个普通角色。改名后权限不变；去掉组织管理员的某项操作码后，该项操作被拒绝。
- 只有 A 角色允许写入、只有 B 角色覆盖目标资源时，不能组合成写入权限。
- 迁移后的资源清单与迁移当时的可见资源一致。之后新建的连接不进入已迁移的授权。
- 旧的 MCP、Agent、Web 插件调用在没有新的功能授权记录时被拒绝。常规查询仍按迁入的数据授权执行。
- 保护「至少一名有效成员同时具备角色维护和组织授权能力」。判断依据是权限码，不是角色名称。

### 阶段 1：角色维护

角色页成为功能权限、数据权限和已授权对象的写入入口。对应原型「角色」。

交付：

- 角色列表，以及创建、编辑、复制、启用、停用、删除。
- 三个 Tab。功能权限编辑权限码。数据权限列出授权给该角色的实际连接 / 资源，列包括名称、类型、关联环境、角色操作、有效期 / 状态和维护操作。已授权对象维护成员或子组织与该角色的分配及有效期。
- 新增数据授权只选择角色、连接资源和有效期。环境、环境组只用于批量勾选，保存前展示完整资源清单，保存时按资源 ID 去重并固定。独立连接可以直接选择。
- 分配角色只选择成员或子组织、角色和有效期。
- 数据权限表格中的单行修改、停用只影响该资源。变更确认写明会影响该角色的全部有效成员。
- 复制角色只复制权限码。删除前检查角色分配、数据授权、待审批申请和审批节点引用。
- 授权中心不再提供新的写入。已有列表和时间线可以暂时只读，避免两套表单同时改权限。

本阶段不做：资源总览六个入口、申请提交、审批流程的连接归属、插件置灰。

验收：

- 数据权限 Tab 没有成员列，也不出现「整个组织」或子组织名称充当资源行。
- 同一角色新增一条独立连接后，所有有效持有该角色的成员获得该角色允许的操作；没有该角色的成员不受影响。
- 复制出的角色没有成员，也没有资源授权。
- 停用或删除会导致组织失去最后一名角色维护者时，操作被拒绝。

### 阶段 2：组织架构收口

子组织详情只承担人员结构和关联资源。角色库和审批流程仍属于整个组织。

交付：

- 子组织页保留成员，以及与资源总览相同的关联资源视图。阶段 3 完成前，关联资源可以先用现有连接列表，但查询范围按设计约定第 2 节计算。
- 邀请只把成员加入子组织，不分配管理角色。新成员继承该子组织及其祖先上已经存在的角色分配和功能授权。
- 一名成员可以属于多个子组织。成员行展示由有效分配计算出的角色，并提供查看权限。
- 环境不设置权限意义上的负责人。展示用的管理人员从有效角色推导，可以是多人。现有文本 `owner` 保留为备注，不转换成授权。

本阶段不做：在子组织页编辑角色或审批流程。

验收：

- 子组织页没有角色目录、授权规则或审批流程编辑器。
- 邀请接受后，成员不会自动获得资源操作码。
- 环境负责人字段的旧文本不能让某人获得环境管理权或成为审批人。

### 阶段 3：资源总览与关联资源

资源总览和子组织关联资源使用同一套视图。前者查询整个组织，后者只缩小范围。

固定六个入口，当前范围没有数据时仍显示零计数和空状态：环境总览、密钥与证书、SSH 工作台、数据库工作台、Redis 工作台、知识库。不设置「全部资源」Tab，不放入连接资源池。默认进入环境总览。

交付：

- 环境总览：搜索、左侧目录（收藏、环境组、未分组）、右侧可折叠的浏览器式环境卡片。卡片统计 Web、SSH、数据库、Redis 数量。
- 密钥与证书、三个工作台、知识库沿用对应用户端的列表结构。日志、服务维护和环境下的 Web 从环境详情进入。未关联环境的 Web、日志、服务出现在环境总览的「未关联环境的资源」中。
- 查询直接使用组织资源集合，包含独立连接、工作空间知识文档、尚未被引用的密钥和证书。共享连接按资源 ID 去重，并列出全部关联环境。
- 环境卡片底部、工作台连接项、资源信息区提供文字按钮「数据授权」或「申请授权」，旁边是「查看授权」。点击后预选当前环境或连接。有维护权限时显示「数据授权」，否则在具备申请权限时显示「申请授权」。
- 地址、账号和其他敏感配置按对应的查看权限显示。目录可见不授予配置或操作能力。
- 收藏与用户端一致：同一环境同时出现在收藏和所属环境组中。收藏不改变授权。

连接的新建、导入、分组和环境关联仍在连接资源池维护。本视图不放「新建环境」、导入、批量删除或实际连接执行。

验收：

- 两个页面里，同一资源的卡片和列表结构一致，子组织只是结果更少。
- 不打开任何环境，也能找到独立连接、工作空间文档和未引用的密钥或证书。
- 只覆盖环境内某一个连接的授权，在环境详情里不会显示成整个环境已授权。
- 使用连接 A 所关联的密钥，不获得连接 B 的使用权，也不获得私钥导出权。

环境总览可以先交付，SSH / 数据库 / Redis 接现有工作台列表，知识库和密钥证书随后。写入按钮依赖阶段 1 的表单。

### 阶段 4：我的授权、申请与待办

侧栏当前身份入口替换组织页面，三个相等 Tab：我的授权、我的申请、待我审批。回到组织架构、资源总览、角色或审批与台账时，回到组织页面。

交付：

- 我的授权分三块：已分配角色、这些角色的数据授权、落到本人的功能授权。管理角色不显示成资源使用权。
- 申请分成「申请数据授权」和「申请功能授权」。数据申请选择申请人已经持有的角色、实际资源清单和时长，并写明该角色的全部有效成员共享。功能申请选择资源范围、功能标记和时长，不选择角色。
- 一次选择跨越多条审批流程时，按流程拆开，不隐式挑选其中一条。阶段 5 完成前，提交可以先关闭，只保留只读的「我的授权」。

本阶段不做：在「审批与台账」里放「申请权限」按钮。申请入口在「我的」。

验收：

- 只持有普通成员时，能看到目录和自己的申请入口，看不到生产资源的操作权限。
- 功能授权列表不出现角色列。数据授权列表不出现功能开关。

### 阶段 5：审批范围、两类申请与台账

把现有的每组织一条流程，改成带授权范围的多条流程。节点能力见设计约定第 6 节。

交付：

- 组织始终保留一条「所有连接」的默认流程，承接尚未划入其他流程的连接，以及以后新增且未分配的连接。
- 指定流程按连接 ID 唯一归属。范围重叠时阻止保存并列出冲突连接。一个连接关联多个环境时，不能按环境拆进不同流程。环境选择只用于批量勾选当前关联的连接。
- 日志源、知识文档、服务维护使用各自稳定的资源 ID，参加同一套归属和授权目标选择。正式存储使用带类型的目标引用；原型里的 `connectionIds` 只是兼容字段名。
- 提交时保存资源清单、节点和审批人快照。按角色选出的审批人在提交时固定为成员列表，并保留选择依据。之后修改流程只影响新申请。
- 数据申请全部通过后，只新增授予目标角色的资源权限，时长从实际生效时起算，不自动分配角色，也不写功能授权。申请人当时已经失去该角色，则阻止授予。
- 功能申请全部通过后，只新增授予申请人的功能授权。拒绝或撤回不生成授权。
- 授权、审批和资源移动写入台账，保留操作人、原因和必要快照。撤销不删除既有台账。导出台账沿用审计导出权限。
- 审批范围的冲突检查和保存在同一事务内完成。

会签、或签、依次审批、抄送、转交、加签、回退可以跟在通过 / 拒绝之后交付。节点在排除申请人后没有合格审批人时，阻止提交并说明原因。只有流程里显式配置的自动通过或自动拒绝才按节点执行。

验收：

- 指定流程覆盖某连接后，默认流程的实际覆盖数减少，该连接只有一个归属。
- 两个环境共享同一连接时，把这条连接划进两条流程会被拒绝。
- 修改流程不改变已提交申请的快照。
- 数据申请通过后，角色分配和功能授权记录保持原样。功能申请通过后，不产生角色分配或数据授权。

### 阶段 6：MCP、Agent、Web 插件执行

功能授权的表在阶段 0 建立，记录的审批在阶段 5 产生。本阶段把执行层接上。范围包括服务端 MCP、桌面 MCP、桌面 Agent 和浏览器插件。

交付：

- 功能授权编辑器没有角色选择。指定单个连接时不能勾选 Web 插件。无法确定真实环境的 Web 访问默认禁用插件。
- 执行前校验真实调用者、目标资源和当前有效授权。Agent 内部再调用 MCP 工具时，渠道仍是 Agent，不额外要求 MCP 功能授权。渠道由可信执行链确定。
- 未获 Web 插件授权的环境继续展示已安装插件，全部为「环境未授权 · 已禁用」。禁用作用于弹窗、内容脚本、后台脚本、快捷键和右键菜单。禁止先注入再置灰。
- 已授权环境仍尊重插件自身的启停。环境授权不自动打开用户已关闭的插件，也不改写全局插件偏好。
- 切换环境、跳转到另一个受管 Web 入口，或授权到期、停用、撤销时，按浏览会话停止当前环境的扩展执行。相同域名在另一个环境中的允许状态不能沿用。

本阶段不做：把 MCP、Agent、Web 插件加进角色权限码。

验收：

- 有生产查询角色、没有生产功能授权时，可以常规查询，自动化调用被拒绝。
- 只有功能授权、没有写操作权限时，MCP 和 Agent 仍然不能写入。
- 开发环境允许插件、生产环境未授权时，生产环境没有内容脚本、后台脚本、快捷键或插件弹窗。用户在允许环境里自己关闭的插件保持关闭。

### 阶段 7：剩余时长与全路径复核

在资源使用位置显示当前用户剩余可操作时长，并在每次执行前重新判定。

交付：

- 环境总览的环境卡片，以及 SSH、数据库、Redis 等工作台连接项，显示有效授权距离到期的剩余时间，例如「可操作剩余 1 小时 20 分」。永久授权不显示。其他资源使用入口使用同一规则。
- 同一操作有多条有效授权时，按并集计算可持续到何时。已有永久授权覆盖该操作时，不因另一条限时授权显示倒计时。
- 同一资源上不同操作到期时间不同时，卡片可以提示「部分操作剩余 …」，详情列出对应连接、操作和到期时间。永久查询与限时写入并存时，仍显示写入的剩余时长。
- MCP / Agent / Web 插件的可用时长同时受功能授权和操作授权约束。两者到期时间不同时分开说明。
- SSH、SFTP、数据库、Redis、知识库、服务维护、连接工具和凭据导出在执行前再次调用阶段 0 的判定。到期后立即重算；仍有其他有效授权时按其继续放行，没有时显示已到期或未授权。
- 数据授权失效阻止对应操作。功能授权失效只阻止对应渠道。

验收：

- 永久授权的连接项没有剩余时长。
- 永久查询、限时写入的连接仍显示写入倒计时，并且查询在写入到期后仍然可用。
- 旧倒计时到期后不能继续放行。停用功能授权后，同一资源的常规查询仍然可用。

## 5. 并行边界

| 可以并行 | 必须等待 |
| --- | --- |
| 阶段 3 的环境卡片和列表样式，使用静态或只读数据 | 阶段 3 的「数据授权」写入，等待阶段 0 和阶段 1 |
| 阶段 4 的「我的授权」只读列表 | 阶段 4 的申请提交，等待阶段 5 的流程匹配 |
| 阶段 6 的执行拦截设计与调用点盘点 | 阶段 6 的实际拒绝，等待功能授权记录能够被审批产生；不能用旧使用权限顶上 |
| 阶段 7 的剩余时长计算单测 | 阶段 7 的界面，等待阶段 3 的卡片和连接项存在 |

阶段 2 的关联资源若早于阶段 3，只交付范围正确的列表，不单独发明一套卡片。阶段 3 的组件完成后替换它。

## 6. 迁移约束

正式迁移的完整要求见设计约定第 7 节。实施阶段 0 时至少同时满足：

1. 旧管理员和旧授权已经具备的操作，用迁移后的角色、分配和数据授权表达，不静默扩大，也不静默丢失。
2. 旧的「整组 / 以后新增的也算」在迁移时拍成资源 ID 清单，不保留动态整组语义。
3. 旧审批流程成为该组织的默认流程。历史申请保留已有快照和审计记录。
4. 同一旧角色曾经按不同人员保存不同资源范围时，按原范围生成可编辑的普通角色副本，避免合并后把最大范围给到每一个原成员。
5. 删除角色不级联删除功能授权。功能授权的有效性不检查 `roleId`。
6. 角色、分配、数据授权或功能授权撤销后，服务端和桌面运行时重新校验。未获插件授权的环境停止扩展执行，存量会话不能绕过。
7. 审批范围的冲突校验与保存在同一事务内完成。

阶段 0 完成前，不删除 `access_authorizations` 和 `resource_grants`。新判定稳定、旧页面不再写入之后，再移除旧的写入路径。
