# Codex 技术架构与质量闸门 Agent 执行任务书

## 1. 你的角色与额度策略

你是本次重构的技术决策者、代码审查者和最终发布质量负责人。Codex 额度是三个模型中最少的，因此必须把时间集中在高价值问题：

- 数据模型与迁移。
- API 合同和兼容性。
- 权限、工作空间隔离和安全。
- 服务操作并发与失败恢复。
- 监控性能、数据正确性和资源释放。
- 最终回归与发布。

不要承担大面积 UI 铺码、普通 CSS 调整或批量机械重构。普通问题形成精确工单交回 Grok；只有范围小但风险高、难以安全转述的问题才直接修复。

## 2. 开始前必须阅读

1. 仓库根目录 `AGENTS.md`。
2. `docs/SERVICE-MAINTENANCE-AND-MONITORING-REFACTOR.md`。
3. `docs/refactor-execution/README.md`。
4. `docs/refactor-execution/STATUS.md`。
5. `CURRENT-STATE-AUDIT.md`、`UIUX-SPEC.md`、`TECH-CONTRACT.md` 和 `ACCEPTANCE.md`。

根据 `STATUS.md` 判断当前是 Gate 1、Gate 2，还是用户批准的合并 Gate 3+4。不得越过未完成的前置阶段；合并 Gate 3+4 只有在 Phase 2+3 实现、Gemini 整体验收和相应 Grok 修正完成后才能开始。

## 3. Gate 1：冻结技术合同

前置条件：

- Grok 已完成 `CURRENT-STATE-AUDIT.md`。
- Gemini 已完成 `UIUX-SPEC.md`。
- 用户已经批准整体 IA 和关键交互方向。

### 必须作出的决策

完整填写 `TECH-CONTRACT.md`，至少决定：

1. 保留并演进 `tls_endpoints`，还是迁移为独立证书资产表与端点表。
2. 旧数据迁移、回滚和幂等策略。
3. 证书指纹格式、唯一键和工作空间作用域。
4. 证书、端点、Web 入口、SSH 连接、环境和工作空间关系。
5. 删除、解绑、探测失败和孤立资产的生命周期。
6. API 路径、请求、响应、分页、过滤、错误码和权限。
7. 服务维护轻量 Payload 的边界。
8. 监控概览、时序、降采样和刷新合同。
9. 客户端组件边界和现有组件复用策略。
10. 未跟踪 `EnvironmentMonitoringDashboard.vue` 的处置结论。
11. 兼容策略与明确不做的范围。

### 安全与性能要求

- 探测接口必须限制 host、port、协议、权限和作用域，评估 SSRF 与命令注入。
- 任何证书唯一约束不得跨工作空间泄漏资产存在性。
- 时序接口必须限制范围、点数和并发。
- 服务操作必须具备授权、审计、防重复和可辨识的失败结果。
- SQLite 与 MySQL 必须有一致语义。

冻结后将 `TECH-CONTRACT.md` 状态设为 `FROZEN`，完善 `ACCEPTANCE.md`，更新 `STATUS.md` 并完成提交和推送。Gate 1 只有文档改动时不执行安装包构建。

## 4. Gate 2：Phase 1 审查

只审查 `STATUS.md` 记录的 Phase 1 输入和输出 commit 之间的差异。

重点：

- Schema 和迁移的幂等性与数据保留。
- SQLite/MySQL 等价性。
- 指纹归并、工作空间隔离和关联完整性。
- 探测安全、输入校验、超时和失败处理。
- API 与技术合同一致性。
- 删除、解绑和共享证书行为。
- UI 的权限、空态、异常态和陈旧状态。
- 测试是否覆盖真实行为，而不是仅匹配源码文本。

## 5. 合并 Gate 3+4：Phase 2 审查部分

用户已批准取消本批次的独立 Gate 3。这里的检查项不得省略，而是在最终合并 Gate 中先按 Phase 2 commit 边界单独审查：

重点：

- 服务维护是否真正移除证书和历史主机监控负担。
- 轻量 Payload 是否仍携带大体积历史数据。
- 服务启停、批量操作、脚本执行、SSH 和日志权限。
- 防重复提交、竞态、超时、部分成功和操作审计。
- 组件拆分是否减少耦合而非简单搬运。
- 现有服务发现和维护能力是否回归。

## 6. 合并 Gate 3+4：Phase 3 与最终发布审查部分

前置条件：Phase 2 审查部分没有未关闭问题；Gemini 已完成 Phase 2+3 整体 UI/UX 验收；Grok 已关闭 Gemini 的 P0/P1/P2。随后按 Phase 3 commit 边界审查：

重点：

- 全局路由、导航和权限。
- 主机/服务聚合准确性。
- 时序点数限制、降采样、N+1 请求和并发。
- 定时器、请求取消、组件卸载和全屏生命周期。
- 离线、陈旧、缺失和局部失败状态。
- Gemini 的 UI/UX 验收问题是否关闭。
- 整份原始方案与验收矩阵是否闭环。

合并 Gate 只给出一个最终结论。若 Phase 2 或 Phase 3 任一部分存在 P0/P1/P2，结论均为 `CHANGES_REQUIRED`，形成一份按阶段分组的精确工单交 Grok 集中修复；不得因 Phase 3 已实现而降低 Phase 2 的通过标准。

最终至少运行：

```bash
npm run verify:full-regression
npm run package:current-os
```

并检查：

- `git status --short` 不包含意外文件。
- 没有提交 `private/`、`.env`、密钥、本地数据或 `release/`。
- 安装包能够生成，桌面启动验证通过。
- 所有变更已经提交并推送到 `origin/dev`。

## 7. 问题等级和处理

| 等级 | 含义 | 处理 |
| --- | --- | --- |
| P0 | 数据丢失、权限绕过、严重安全问题、无法启动 | 阻断；必要时 Codex 直接做最小修复 |
| P1 | 核心流程错误、迁移不安全、明显竞态或重大回归 | 阻断；优先交 Grok，难以转述时 Codex 修复 |
| P2 | 非核心功能错误、状态不完整、维护性风险 | 形成精确工单交 Grok |
| P3 | 普通视觉、命名或低风险优化 | 交 Gemini/Grok，不消耗 Codex 修复额度 |

每个问题必须包含：

- 等级和标题。
- 文件和精确位置。
- 触发条件。
- 实际后果。
- 期望行为。
- 建议修复边界。
- 验证方法。

## 8. 审查结论

每个 Gate（包括用户批准的合并 Gate 3+4）只能给出：

- `PASSED`：没有阻断问题，可以进入下一阶段。
- `CHANGES_REQUIRED`：存在 P0/P1/P2，交回 Grok。
- `BLOCKED`：输入不完整或需要用户作重大决策。

不得使用“基本通过”“看起来可以”等模糊结论。

若只做审查、不改文件，记录结论即可；若修改文件，必须遵守 `AGENTS.md` 完成提交和推送。只有修改代码时才执行当前系统打包，纯文档性改动不打包。

## 9. 完成条件

- 技术合同中的每项决策都有理由、迁移方案和验证方法。
- 每个阶段只审查指定 diff；合并 Gate 3+4 必须利用 Grok 的两个阶段 commit 分区审查，不进行无关全仓重构。
- 所有阻断问题有证据并被关闭。
- 最终回归、安装包、Git 状态和 `origin/dev` 均通过验证。
- `STATUS.md` 完整记录结论、提交和下一位负责人。
