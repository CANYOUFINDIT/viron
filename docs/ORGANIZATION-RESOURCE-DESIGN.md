# 组织、角色与资源授权设计约定

状态：已确认的产品设计与参考原型，尚未接入正式业务后端。

日期：2026-10-07。

参考原型：[`prototypes/organization-resources.html`](../prototypes/organization-resources.html)。

本文件记录本次讨论最终确认的约定，作为后续实施、迁移和验收依据。原型中的账号、地址、人员和业务名称均为虚构示例，不能作为正式产品的限制或默认配置。原型行为与本文件不一致时，应按本文件核对修正，不应把演示数据或未实现的入口理解为产品规则。

## 1. 目标与既有资源体系

保留 Viron 的组织、子组织、环境组、环境及独立连接体系，重新整理管理权、资源操作权和功能使用权。

| 对象 | 约定 |
| --- | --- |
| 组织 | 工作空间、成员及资源的数据边界；统一维护角色、授权、审批与台账 |
| 子组织 | 人员分组与层级；成员继承本级及祖先子组织的授权；一个成员可属于多个子组织 |
| 环境组 | 对环境进行业务分类，也是可选择的资源授权范围 |
| 环境 | 聚合 Web、SSH、数据库、Redis、日志、知识库与服务维护资源；Web 插件按当前访问环境进行功能授权 |
| 连接 | 独立存在，可不关联环境，也可关联多个环境；必须能直接检索、授权与匹配审批流程 |
| 证书、密钥 | 主资源的关联记录或认证依赖，不作为与连接平行的资源使用授权对象 |

不得只通过环境查询连接，否则会遗漏未关联环境的资源。环境、团队职责关联及人员名称本身都不授予权限。

## 2. 页面与数据维护层级

组织工作空间设置并列入口：组织架构、资源总览、角色、审批与台账，以及个人的授权、申请与待办。移除重复的“授权规则”菜单。角色分配记录仍然存在，在角色详情和对应资源详情中维护，不再建立另一套授权规则。

- 子组织详情仅展示人员结构、成员及关联资源，不放置角色与审批流程等全局维护模块。
- 角色目录、授权记录和审批流程属于整个组织。子组织可作为授权对象、管理范围或查询条件，不拥有另一份角色库和审批流程库。
- 组织级入口不意味着所有成员都能维护；操作仍由有效角色权限与范围决定。
- 子组织页面查看关联资源时可以预填成员范围，但不能改变角色和授权数据的组织级归属。
- 组织级“资源总览”保持原名称，是查看该组织全部资源数据的位置，不能改成授权统计页。展示入口、排列方式和列表样式沿用 Viron 用户端的使用视角；“组织架构 → 关联资源”复用同一套视图组件，只改变资源查询范围。
- 一级展示 Tab 与当前用户端资源菜单对应：环境总览、连接资源池、密钥与证书、SSH 工作台、数据库工作台、Redis 工作台、知识库。不设置“全部资源”Tab；默认进入环境总览。固定保留这些入口，即使当前范围没有数据也显示零计数和空状态，不根据演示数据隐藏菜单。

| 展示 Tab | 与用户端一致的列表结构 |
| --- | --- |
| 环境总览 | 搜索与筛选条；左侧环境目录含收藏、环境组、未分组；右侧环境组标题与可折叠卡片网格；环境卡片沿用浏览器标签栏、地址栏、名称/说明及 Web、SSH、数据库、Redis 四类数量块 |
| 连接资源池 | SSH、数据库、Redis 库存统计与筛选；按连接组折叠的库存表格，展示名称、类型、地址、连接方式、关联环境、连接组、来源、巡检状态与凭据元信息 |
| 密钥与证书 | SSH 密钥 / SSL/TLS 证书子分类；密钥概要和横向密钥卡片；证书状态概要和证书卡片；保留连接引用信息，组织级查询也包含尚未引用的记录 |
| SSH 工作台 | 搜索、连接组与主机卡片，展示名称、账号/地址及标签 |
| 数据库工作台 | 搜索、连接组与紧凑数据库连接导航列表 |
| Redis 工作台 | 搜索、连接组与 Redis 连接项，展示名称、地址和数据库编号 |
| 知识库 | 文件夹 / 文档树及文档预览；包含独立的工作空间文档 |

- Web 入口、环境日志、服务维护和环境内知识资源在环境详情中沿用对应资源分类展示，不另造与用户端菜单不一致的一级 Tab。日志、脚本、服务和主机监控仍保留真实资源对象与授权目标。若存在未关联环境的 Web、日志或服务资源，环境总览另列“未关联环境的资源”目录段，可直接定位该资源；不得为了分组强制其关联环境。
- 浏览样式与资源维护职责分别处理：组织的资源总览展示上述数据和列表结构，连接配置、创建、导入、分组与环境关联仍在正式连接资源池维护；原型不放置“新建环境”、导入、批量删除或实际连接执行入口。
- 列表主体展示资源本身的数据，不能统一替换成“数据授权覆盖人数 / MCP 人数 / Agent 人数 / 插件人数”的授权统计表。地址、账号及其他敏感配置按对应查看权限判定；目录可见不自动授予配置或操作能力。
- 资源详情提供“数据授权”和“功能授权”：前者展示角色分配及数据范围，后者维护 MCP / Agent / Web 插件的独立授权对象、资源范围与有效期。查看、申请或维护授权不会改变一级页面“资源总览”的定位。
- “角色”集中维护所有功能权限信息：角色名称、说明、操作权限码、启停状态、创建、编辑、复制和删除；角色详情的“已授权对象”直接查看、分配、修改、停用或撤销成员/子组织的角色分配、数据范围与有效期。MCP / Agent / Web 插件的使用许可继续在具体资源的功能授权中维护，不纳入角色的操作权限码。
- 选择整个组织时，直接从组织资源集合查询，包含未关联环境的独立连接、工作空间知识文档、未引用的密钥和证书；不得先查询环境再拼接连接。独立资源可直接查看详情、授权、申请和匹配审批流程。
- 选择子组织时，聚合本级及下级的职责关联资源、子组织授权、沿祖先子组织继承的授权，以及这些成员的数据与资源功能直接授权。只关联功能授权的资源也可以定位，但不因此获得操作权限。连接授权按资源 ID 查询，不依赖该连接是否关联环境；单个连接的授权不扩大为整个环境授权。
- 资源详情显示关联来源，并区分“未关联环境”和“关联多个环境”。共享连接在工作台/库存中按资源 ID 去重，保留全部关联环境；同一个收藏环境同时出现在收藏和所属环境组中，与用户端排列一致，不把收藏当成另一个环境对象。职责关联、目录可见以及单独的功能授权都不表示已授予操作权限。
- 连接资源池保留未关联环境与多环境关联筛选。各工作台可直接检索独立连接，知识库可直接检索工作空间文档，无须从环境进入。切换一级 Tab 时重置搜索及当前类型筛选，避免上一页条件隐藏下一页数据。
- 环境授权详情只汇总覆盖环境范围的授权；只覆盖环境内某个连接的授权在该连接详情中查看，不能显示成已获得整个环境的操作权。子组织授权详情的成员统计限定本级及下级成员。

## 3. 统一角色模型

### 3.1 创建组织时的初始角色

创建组织时生成三个普通角色：组织管理员、普通成员、审计员，并把初始组织管理角色授权给创建者。

| 初始名称 | 初始内容 |
| --- | --- |
| 组织管理员 | 用权限码明确表达现有组织管理员的管理及资源操作能力，后续可修改 |
| 普通成员 | 目录浏览、发起申请及自己的申请与授权入口；加入组织不自动获得资源操作能力 |
| 审计员 | 查看授权、审批及台账，不执行资源操作 |

这些名称只描述初始内容，不具有特殊语义。初始角色和后续创建的角色使用同一张表、同一套规则，允许编辑权限、改名、复制、启停和删除。不得通过 `builtIn`、`systemRole`、角色名称或固定角色 ID 获得额外能力。

原型示例组织另有后来创建的“生产查询”和“开发协作”两个业务角色，用于展示使用场景；它们不是创建组织时必须生成的默认角色。

### 3.2 功能权限、数据权限与资源功能授权

这三个概念分别回答不同问题，不能放进一条角色记录混合维护：

| 类型 | 回答的问题 | 保存位置 | 示例 |
| --- | --- | --- | --- |
| 功能权限（操作权限） | 能做什么 | 角色的权限码集合 | 数据库查询、写入、SSH 登录、邀请成员、维护审批流程 |
| 数据权限（生效范围） | 谁可以对哪些数据或资源执行这些操作，在何时生效 | 角色分配记录：对象 + 角色 + 数据范围 + 有效期 | 订单研发使用查询角色，仅覆盖订单生产主库，持续 2 小时 |
| 资源功能授权 | 谁可以在指定资源上使用特定执行渠道或扩展功能 | 独立的资源功能授权：对象 + 资源范围 + 功能 + 有效期；不含角色 | 订单研发仅在开发与测试环境使用 MCP、Agent、Web 插件 |

管理操作与资源使用操作分别定义权限码，统一由普通角色保存。MCP、Agent、Web 插件仍按之前约定作为资源功能授权，不纳入角色权限码目录。角色中的“创建授权”等权限码控制谁能维护授权，并不表示此人自动获得 MCP、Agent 或插件使用权。

```text
角色：查询 / 写入 / 登录 / 组织管理等操作权限
   ↓
角色分配：成员或子组织 + 角色 + 数据范围 + 有效期

资源功能授权：成员或子组织 + 环境或连接 + MCP / Agent / Web 插件 + 有效期
             （独立记录，不含 roleId）

常规操作 = 存在有效角色分配，且角色允许该操作、数据范围覆盖目标
MCP / Agent 操作 = 常规操作条件满足 ∧ 目标的有效资源功能授权
Web 插件使用 = Web 入口有效访问权限 ∧ 当前环境的有效插件功能授权 ∧ 插件自身启用
```

- 角色定义能做什么；角色分配定义哪些成员、哪些数据范围以及何时生效。不另外定义脱离角色的读写操作授权。
- 数据范围支持组织、子组织、环境组、环境、连接；可表示独立连接和共享连接。组织级操作码仅在组织范围分配中生效，不能通过向单个连接分配角色获得组织管理能力。
- 资源功能授权对象仍是成员或子组织，目标是环境或连接；环境组可用于批量指定环境。新建资源功能授权不提供组织管理范围或角色选择。
- 子组织数据管理范围是否包括下级需明确配置；人员从祖先子组织继承授权的规则继续保留。
- 每条角色分配必须同时满足操作码与数据范围，才纳入有效操作并集。不能从 A 分配取写操作码、从 B 分配取数据范围拼出原本未授予的写操作。
- 修改、改名、更换、停用或撤销角色及角色分配，不改写独立的资源功能授权；操作权限失效时实际 MCP / Agent / 插件执行仍被阻止。之后恢复数据授权时，在原功能授权仍有效的前提下重新计算可用性。
- 资源功能授权有自己的开始时间、结束时间和启停状态。修改、停用或撤销它不改变角色和数据范围；例如功能授权到期后仍可进行有效数据授权覆盖的常规查询。
- 同一资源功能的允许值取覆盖目标的有效功能授权并集；未勾选是未授予，不是覆盖其他记录的显式拒绝。功能有效性只检查其自身对象、范围与时间，不检查某个 roleId。
- 必须保护组织最后的有效角色维护与组织授权能力；保护条件针对实际权限，不针对某个初始角色。
- 授权维护能力与资源使用能力分开判断，不能因为能维护授权就绕过资源权限。独立功能授权本身既不授予数据访问，也不扩大已有操作权限。

正式实施必须替换组织成员 `admin/member` 的硬编码管理员放行逻辑，包括组织接口、资源接口、审批、连接工具、凭据维护及桌面执行路径。角色名称不参与审批人兜底或权限判断。个人工作空间所有者及平台管理的既有边界单独保留，不借此获得组织资源权限。

### 3.3 账号与关联凭据

连接已有固定账号时，先按连接授予角色操作权，执行使用连接已配置的账号；不使用一个字符串给多条异构连接虚构统一登录账号。未来支持一个主资源的多个托管账号时，账号限制作为授权约束记录，不能通过账号选择扩大角色操作权限。

- 允许使用连接时，系统可以使用关联认证密钥完成认证，无需用户另行获得“密钥使用权”。
- 同一密钥关联 A、B 两个连接，获得 A 的使用权限不获得 B 的权限。
- 连接使用权限不自动允许查看私钥明文、导出私钥、替换或删除共享密钥。
- 证书记录可随主资源显示；证书探测、凭据维护、私钥导出是角色中的独立管理操作。
- 证书与密钥可保留集中维护页面，展示引用关系，避免误改共享依赖。

### 3.4 资源使用界面的剩余可操作时长

本次新增的实现要求：在资源使用位置显示当前用户剩余被授权的可操作时长，包括环境总览的环境卡片，以及 SSH、数据库、Redis 等工作台的连接项；其他资源使用入口遵循同一规则。此项已记录，尚未接入正式使用界面。

- 显示的是有效授权距离到期的剩余时间，例如“可操作剩余 1 小时 20 分”，不是累计使用额度或在线会话时长。永久授权不显示剩余时长。
- 按真实资源和具体操作计算，包含直接、子组织继承及环境范围授权；独立连接和共享连接同样适用，不因页面所在环境不同而改变到期时间。
- 同一操作存在多条有效授权时，按并集计算可持续操作至何时；已有永久授权覆盖该操作时，不因另一条限时授权显示倒计时。已停用、撤销、到期或尚未生效的授权不能计入可操作时长。
- 不同操作或资源的到期时间不同，卡片可提示“部分操作剩余 …”，详情列明对应连接、操作及到期时间。永久查询与限时写入并存时，仍显示写入的剩余时长，不能把整个资源标为永久可操作或统一到期。
- MCP / Agent / Web 插件的可用时长还须同时满足功能授权与操作授权；若到期时间不同，在相关入口或详情分别说明，不混为常规操作的时长。
- 剩余时间随时间和授权变更刷新。到期时立即重新计算实际权限，更新按钮、连接项及执行入口；有其他有效授权时继续按其计算，没有时显示已到期或未授权，不能保留旧倒计时继续放行。

## 4. 环境不设置权限意义上的负责人

取消本方案中的环境“负责人”字段，不引入由字段赋值获得环境管理权或审批责任的机制。

- 环境管理人员从有效角色授权推导展示，可能是多人。
- 环境组、说明及团队职责关联可以保留；它们是组织和业务信息，不直接授予权限。
- 审批人由流程节点配置，不根据环境负责人字段隐式产生。
- 正式迁移现有文本 `owner` 字段时，可保留为历史备注或经过确认后移除，但不得转换为权限授权。

## 5. MCP / Agent / Web 插件是功能授权

### 5.1 MCP / Agent

MCP 和 Viron AI Agent 不作为权限码，不进入角色权限码目录。它们是针对被授权成员或子组织、目标环境或连接的功能使用授权。

独立的 `resourceFeatureGrants` 记录分别配置 `features.mcp` 和 `features.agent`，默认均为未授权，不含 `roleId`。角色仍定义资源的具体操作；功能授权只决定可以通过哪个渠道执行这些操作。

```text
允许一次执行 = 目标资源的有效操作权限 ∧ 该目标的有效 MCP 或 Agent 功能授权
```

| 场景 | 常规操作 | MCP / Agent |
| --- | --- | --- |
| 有开发环境操作角色，并获得开发环境功能授权 | 按角色执行 | 按同一角色操作范围执行 |
| 有生产环境查询角色，没有生产环境功能授权 | 可以常规查询 | 禁止调用，即使其他环境允许自动化 |
| 有功能授权，没有写操作权限 | 不能写入 | 仍不能写入 |
| 功能授权到期、撤销、停用，数据授权仍有效 | 继续按角色与数据范围执行 | 禁止对应渠道，不能保留旧会话放行结果 |

原型将角色分配和资源功能授权保存在两个集合中，分别维护人员、资源范围与有效期。角色分配编辑器没有功能开关，功能授权编辑器没有角色选择。有效标记仅按覆盖同一目标的生效功能授权计算；未勾选表示未授予，不是能否定其他生效授权的显式拒绝。若组织希望生产完全禁用，所有覆盖生产目标的功能授权都应不授予该功能；维护环境组等批量范围时需展示实际目标，避免覆盖这些生产目标。

共享连接按实际连接身份计算，环境只是授权范围的选择方式，不因切换当前页面而产生另一份连接权限。环境范围会覆盖关联连接，维护授权时必须展示共享连接关联了哪些环境，避免误把共享生产连接纳入开发功能授权。

- 执行前校验真实调用者、目标资源及当前有效授权；不能只隐藏入口或只检查当前环境名称。
- 服务端 MCP、桌面 MCP 和桌面 Agent 的直接执行都遵循同一判定。
- Agent 内部复用 MCP 工具时，执行渠道仍是 Agent，不要求同时拥有 MCP 功能授权；来源由可信执行链确定，不能由任意客户端字段冒充。
- 资源授权审批与 Agent 执行前确认分别保留。执行前确认不能替代权限授权或扩大权限。
- 审计明确记录真实用户、角色授权依据、目标、操作及调用渠道。

### 5.2 Web 插件按环境授权

新增 `features.webPlugins`，默认未授权，不新增角色权限码。和 MCP / Agent 一样，独立绑定被授权成员或子组织、资源范围及有效期，不绑定角色；Web 插件的使用判定按当前访问的真实环境进行。

```text
允许使用某个 Web 插件 = 当前用户具有该 Web 入口的有效访问权限
                       ∧ 当前环境的有效 Web 插件功能授权
                       ∧ 该插件本身已启用
```

- 新建功能授权通过环境或环境组指定目标；兼容迁移的旧记录按原有范围覆盖环境。插件功能标记仅按覆盖当前环境的有效功能授权取并集。与 MCP / Agent 保持相同规则：未勾选表示未授予，不是对其他有效授权的显式拒绝。要禁止生产使用插件，所有覆盖生产环境的授权都不能授予该功能。
- 指定单个连接的授权不授予整个环境的 Web 插件使用权。参考原型在功能授权编辑器的连接范围禁用插件勾选项；无法确定真实环境的 Web 访问默认禁用插件。
- 未获 Web 插件授权的环境，插件菜单继续展示已安装插件，但全部置灰、显示“环境未授权 · 已禁用”；插件打开按钮、工具栏入口和启用操作全部禁用。不能通过用户手动启用、固定插件或另一个环境的已启用状态绕过。
- 禁用必须作用于执行层：禁止扩展弹窗、内容脚本注入、后台脚本或 service worker、快捷键、右键菜单等执行入口。已安装插件和用户个人启停偏好可保留，不能为了禁用某个环境而卸载插件或改写全局偏好。
- 环境允许使用插件时，仍尊重插件自身的启停状态；环境授权不自动启用用户已停用的插件，也不赋予新的资源访问或 Viron API 权限。
- 判定依据真实用户、Web 入口及其可信环境上下文，不根据 URL、域名或页面名称猜测。相同网站在开发环境允许插件、生产环境未获授权时，生产仍全部禁用；共享 Web 入口也按当前环境分别判定。
- 网页访问前确认插件授权，禁止先加载插件、注入脚本后再置灰。切换环境、跳转到另一个受管 Web 入口，或授权到期、停用、撤销时立即重算；按浏览会话隔离环境状态，关闭或停止当前环境的扩展执行路径，不能沿用允许环境的插件会话。
- 申请、审批快照、授权详情和台账保留 `webPlugins` 标记；旧授权缺少该字段按未授权处理，不从“插件已安装”、管理员角色名称或旧 Web 访问权限推断允许。
- 原型演示独立功能授权的勾选、保存、审批及环境内全部禁用的状态预览，使用虚构插件；正式桌面和浏览器运行时的插件加载与权限接口尚待接入该判定。

## 6. 审批流程直接配置授权范围

### 6.1 范围与唯一归属

每条审批流程直接增加授权范围，支持“所有连接”或“指定连接 / 环境”。不引入组织—环境组—环境的多层流程继承和优先级覆盖规则。

- 组织仅保留一条“所有连接”默认流程，初始承接所有连接。
- 指定流程选中连接后，该连接从默认流程的实际范围移出。
- 默认流程实际覆盖未划入其他指定流程的连接，以及以后新增且未分配的连接。
- 指定范围之间不能重叠：同一个连接只能对应一个流程。发现重叠阻止保存并列出冲突，用户先明确调整原归属，不自动覆盖。
- 一个连接关联多个环境时，按连接 ID 去重和检查唯一归属，不能按环境分别归入不同流程。
- 环境选择用于批量勾选当前关联的连接，保存后的连接清单是实际范围。新增连接不会暗中挤入某条指定流程；未分配时由默认流程承接。
- 编辑流程必须展示实际覆盖的连接，连接详情展示唯一对应的流程。
- 独立连接直接参与范围选择与匹配，不能因为未关联环境而没有审批流程。

### 6.2 节点与申请

保留多节点审批、指定成员或按角色选择审批人、任一人通过、会签、顺序审批，以及节点可配置的抄送、转交、加签、回退。

- 审批人需具有对应资源范围的审批权限，角色名称不提供特殊资格。
- 排除申请人后无人可审批时阻止提交并说明原因；不得因节点无人而隐式自动通过。显式配置的自动通过 / 自动拒绝节点按流程执行。
- 申请明确区分“数据授权申请”和“功能授权申请”。数据申请包含角色、数据范围与时长，不包含功能开关；功能申请包含资源范围、功能标记与时长，不包含角色。两者按目标匹配同一套审批流程，审批详情显示类型及对应内容。
- 提交时确定流程，保存资源范围、节点与审批人快照。角色方式选出的审批人也应在提交时固定为成员列表，同时保留选择依据；实际处理时重新检查成员及权限有效性。
- 流程名称、范围、节点或审批成员后续变更只影响新申请，不重定向已有申请。
- 一次请求若覆盖多个流程，不隐式选其中一条。参考原型明确要求按流程分别申请；正式产品可以显示分组并批量提交，但必须让申请人看清各组范围和流程。
- 申请期间若资源关联变化导致实际范围改变，阻止沿用旧审批授予新增范围，要求按当前范围重新申请。
- 通过后仅生成该申请类型对应的角色分配或独立功能授权；功能申请审批通过不能自动生成角色分配。时长从授权实际生效时开始计时。拒绝或撤回不生成授权。
- 授权、审批和资源移动留存操作人、原因与必要快照；删除或撤销不能删除既有台账。

没有资源的空环境暂由组织默认流程承接。日志源、知识文档和维护对象使用各自稳定的目标 ID，参与角色授权和审批范围；它们不因此变成 SSH、数据库或 Redis 连接。参考原型将这些对象与连接一起放入授权目标选择器，沿用同一默认流程和唯一归属规则，不能遗漏或因无连接而绕过审批。原型的 `connectionIds` 字段兼容记录这些资源 ID，正式实施应使用带类型的授权目标引用。

## 7. 建议的数据结构与迁移要求

角色、数据授权和资源功能授权分别建模：

```text
roles: id, organizationId, name, description, enabled, permissionCodes
roleGrants: id, organizationId, subjectType, subjectId, roleId,
            scopeKind, targetIds, includeChildren, startsAt, expiresAt,
            enabled, reason, source, requestId
resourceFeatureGrants: id, organizationId, subjectType, subjectId,
                       scopeKind, targetIds, startsAt, expiresAt, enabled,
                       features { mcp, agent, webPlugins }, reason, source, requestId
approvalWorkflows: id, organizationId, name, scopeMode, targetIds, nodes
accessRequests: id, requesterId, kind { data | feature }, targetSnapshot,
                duration, workflowSnapshot, stage, decisions, grantIds,
                roleId (仅 data), features (仅 feature)
```

两个授权集合分别保存、校验与记录审计；`roleGrants` 不含 `features`，`resourceFeatureGrants` 不含 `roleId`。删除某个角色不得级联删除资源功能授权。参考原型沿用 `db.grants` 表示角色分配，另设 `db.featureGrants` 表示资源功能授权。

参考原型 v9 将浏览器 v8 保存的显式功能标记复制为独立功能记录，保留对象、范围与有效期，并从原角色分配移除标记。旧记录的角色已停用时，迁出的功能记录也设为停用，避免迁移时恢复原已失效的功能；缺失或未勾选的标记不生成允许记录。旧的待审批混合申请仅为兼容保留原快照，通过后生成两条独立记录；新申请只能选择数据或功能一种类型。这是演示存储迁移，不代表正式数据库迁移已完成。

正式落地必须同时完成：

1. 初始化普通角色和创建者绑定，替换旧管理员身份的权限捷径。
2. 保留旧管理员及旧授权已具备的操作，通过迁移角色和绑定表达，不能静默扩大或丢失权限。
3. 旧审批流程成为组织默认流程；历史申请保留已有快照和审计记录。
4. MCP / Agent / Web 插件初始功能授权采用明确策略；不得从旧资源使用权限或已安装插件自动推断已允许自动化或扩展执行。
5. 环境管理人员从角色推导；证书、密钥引用关系继续保留。
6. 角色、绑定和功能授权撤销后的服务端与桌面运行时重新校验；未获插件授权的环境停止扩展执行，避免存量会话绕过新规则。
7. 审批范围在同一事务内执行冲突校验与保存，防止并发造成重复归属。

原型仅演示这些约定，不包含数据库迁移、正式 API、真实连接、秘密材料或 MCP / Agent 执行。

## 8. 验收场景

- 子组织详情仅出现成员与关联资源；角色与流程统一在组织级维护；没有独立“授权规则”菜单。
- 新组织只生成三个普通角色；任何角色改名后权限不变，修改权限后现有引用同步变化。
- 移除初始管理角色的资源操作码，会失去对应操作；不会由于名字叫管理员继续放行。
- 同一角色能分别限定开发与生产数据范围；独立资源功能授权只覆盖开发时，生产常规查询可用而自动化调用被拒绝。
- 仅有 MCP / Agent 功能授权不能获得未授予的写操作；角色或授权停用后功能也不可执行。
- 同一用户在开发环境可使用 Web 插件、生产环境未获授权时，生产插件列表全部禁用；相同域名和共享 Web 入口不能使生产沿用开发的允许状态。
- 未获授权的环境没有内容脚本、后台脚本、快捷键或插件弹窗执行；到期、撤销或切换环境时同步停止。允许环境中用户自己停用的插件仍保持停用。
- 独立 Web 插件功能授权标记随功能申请审批及其自身有效期保留；旧授权缺失标记时默认禁用，不新增角色权限码。
- 没有关联环境的连接可直接授权、申请、查看审批流程。
- 两页均没有“全部资源”Tab 或“新建环境”按钮；一级 Tab 与当前用户端资源菜单一致。环境总览使用环境目录、分组和浏览器式卡片；密钥证书、各工作台和知识库分别使用自身列表样式，日志和服务维护从环境详情定位。
- 在对应视图中可以直接找到未关联环境的独立连接、工作空间文档和未引用的密钥证书，不需要先打开某个环境。资源总览主列表展示数据，授权在详情维护；不提供连接配置、导入和连接分配操作。
- 同一资源在“资源总览”和子组织“关联资源”中的卡片/列表结构相同；子组织只缩小查询范围。收藏与环境组采用同一环境 ID，个人收藏不改变授权。
- 子组织获得独立连接的直接授权、上级继承授权或成员直接授权后，关联资源中能找到该连接；共享连接只显示一条，并列出其全部关联环境。
- 使用 A 连接的认证密钥不获得 B 连接的使用权，也不获得私钥读取或导出权。
- 环境不设负责人；其管理人员随有效角色授权变化。
- 指定流程覆盖连接后，默认流程实际覆盖数减少；连接没有重复归属。
- 两个环境共享同一连接时，冲突必须被识别；不同名称不影响唯一性。
- 修改流程不改变已提交申请；全部节点通过后，按申请类型生成角色分配或独立资源功能授权，并从此刻计时。
- 修改、启停、撤销和审批行为记录到台账；两类到期分别重算：数据授权失效阻止操作，功能授权失效只阻止对应功能。
- 资源使用界面显示限时操作的剩余时长；永久授权不显示。同一连接永久查询、限时写入时仍显示写入倒计时；到期时按其他有效授权重新计算，不一律断言整个连接失去全部权限。

- 角色详情直接维护已授权成员及子组织、数据范围和有效期；数据授权编辑器没有 MCP / Agent / Web 插件开关，资源功能授权编辑器没有角色选择。
- 修改或更换角色，不修改资源功能授权记录；数据权限仍允许时原功能继续有效，数据权限不允许时实际执行被拒绝。停用功能授权不会撤销常规操作的数据权限。
- 只有功能授权没有对应操作码或数据范围时，MCP / Agent 与插件实际使用仍被拒绝；不同角色分配不能把操作码和数据范围交叉拼接后放行。
